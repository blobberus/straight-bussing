# Straight Bussing for iPhone (native SwiftUI draft)

A native SwiftUI version of the web app in `web/`, started 2026-10-09 (owner request: "begin drafting the code" for the
App Store transition, plus a browsable simulation). It is compiled, unit-tested, UI-tested and run in the iOS
Simulator on GitHub's free macOS runners on every push that touches `ios/` or `web/data/`. No Mac is needed to work on
it; a Mac is only needed to run it interactively or to ship it.

**See it running:** https://blobberus.github.io/straight-bussing/ios/ (screenshots in light and dark mode, two
walk-through recordings and the App Store screenshot set from the iOS Simulator, regenerated by CI; `-demo` mode with
simulated buses, shown the way riders see real service: no demo label, owner decision 2026-10-11).

**Design rules:** `docs/DESIGN.md` "1b. System rules" as iOS tokens in `Shared/Palette.swift` (colors, contrast, radius
scale); audit and contrast table: `ios/DESIGN-AUDIT-2026-10-10.md`. **Privacy policy / support:**
https://blobberus.github.io/straight-bussing/privacy.html and `/support.html` (`web/privacy.html`, `web/support.html`),
linked from About and Settings.

Unofficial student project. Not affiliated with the University. Official service: 773.702.8181.

## Layout

```
ios/
  StraightBussingKit/     Swift package: all pure logic (port of web/js/core + web/js/data), XCTest suite
  App/Sources/            SwiftUI app: Model/ (state, polling, prefs, location, Live Activity, bus alerts), Views/
  App/Resources/          Asset catalog (icon rendered at build time), PrivacyInfo.xcprivacy
  Shared/                 Code in both the app and the widget extension (ActivityAttributes, Live Activity views)
  Widget/                 Widget extension: trip Live Activity (Lock Screen + Dynamic Island)
  UITests/                XCUITest smoke test (tabs, swipe actions, delete confirmation, Directions -> Start)
  scripts/                bootstrap.sh (icon + XcodeGen), simulate.sh (CI screenshots/recordings + App Store set),
                          gallery.py, pick_simulator.py, store_png.py, ...
  project.yml             XcodeGen spec (the .xcodeproj is generated, never committed)
```

`web/data/*.json` is bundled into the app at build time through a folder reference in `project.yml` (`../web/data`,
copied as `data/` in the app bundle). It is never duplicated in `ios/`; the daily GTFS refresh flows into the next
build, and between builds the app downloads newer files from the web app's site (see "Schedule updates" below). The app icon is rendered from `web/icons/icon.svg` by `scripts/make_icon.py` (fallback: `sips` upscales
`web/icons/icon-512.png`).

`StraightBussingKit/Tests` reuse the web tests' fixtures and expectations (web/tests/core-*.js, route-schedule.js,
data-geocode.js) so the Swift port provably behaves the same.

### Trip progress (owner request 2026-10-09)

When a trip is started (Directions > option > Start), the Current trip tab shows the web's Google-Maps-style
timeline (`Views/TripTimelineView.swift`, data from `TripFollow.compute`, a port of web core/tripprogress.js, words
from `TripText`): "Trip to X" with the arrival estimate and End trip, a status card for the phase (walk N min to the
stop + "Leave in N min, est." / bus N stops away / "Get off in N stops: X" / walk to the destination), walk rows, each
bus leg with up to 3 stops before the boarding stop while the bus is coming, "Board here" / "Get off here",
"Passed" on passed stops, "Bus 101 heading here", the bus chip on the line between the right stops, live ETAs from
that bus's own prediction, then the destination, "Trip steps" and an honesty footnote. The planned VEHICLE is
followed (Passio gives several buses one trip id); if your location is still at the stop after it left, the next
bus is followed ("Your planned bus has left. Showing the next one."); without live data the plan's clock is
followed and said so. Picking another card in Directions during a trip makes the timeline follow it; changing an
endpoint ends the trip. The same data feeds the Live Activity (`TripFollow.snapshot` -> `LiveTripSnapshot` = the
ActivityKit ContentState): Lock Screen card with the
arrival in whole minutes (see "Live Activity times" below), the next stops as a progress bar with the bus, "est." and
"Unofficial" labels; Dynamic Island compact "53RD | 3 stops 4 min" (on board "2 left" / "Next stop" / "Get off",
the timeline's count; iOS 17: "53RD | 6:37 PM"), expanded progress bar + boarding/alighting names, minimal route dot.

### You on the trip map, trip alerts in step with it (owner request 2026-10-13)

"The Current Trip map should show the user's location in the current trip's location (especially for bus routes).
Make this sync to the notification center's get off in X stops." Same spec and strings as the web (trip-you-web,
web/js/core/tripyou.js, core/notify.js tripAlerts, ui/tripmap.js). `AppModel.refreshTrip` makes ONE `TripFollow` per
refresh (poll, clock tick, location fix, return to the app) and everything reads that value with the same `now`: the
timeline (`tripFollow`), the map (`tripYou`, Kit `TripYou.compute`), the Live Activity (`snapshot`) and the trip
alerts (`checkTripAlerts`, Kit `Notify.tripAlerts`). So the card, the map label, the alert and the Dynamic Island say
the same count: "Get off in 2 stops: Medical Center" (`TripText.offText`; stopsLeft 0 = the bus is at your stop, 1 =
your stop is next).
- **Map** (`Views/MapScreen.swift`): on the bus you ride, an accent ring and a "You" pill on its marker (they glide
  with it; MapKit's user dot steps back); while waiting without GPS a dashed ring at the boarding stop with
  "You (est.)"; otherwise the normal user dot. If your accurate GPS (<= 100 m) is more than 300 m + its accuracy from
  the bus, your GPS is shown and the card adds "Your location is not near Bus 101. Stop counts follow the bus."
  Labels: "Board here" under the boarding stop before boarding, the get-off count ("Get off in 2 stops" / "Get off
  next stop" / "Get off here") above the alighting stop until arrived. VoiceOver reads the You marker's sentence.
- **Follow camera** (`Model/AppModel+Follow.swift`): on at Start and by the locate button during a trip (it then
  reads "Show me on my trip", asks for location the first time); off when the rider drags or zooms
  (`MapCameraPosition.positionedByUser`) or another screen moves the map. While on it frames `TripYou.frame` (you,
  what you head for, the coming bus when <= 3 stops away) on a phase or leg change, or when a framed point leaves the
  visible map (below the floating chrome, above the sheet: RootView measures it, `MapProxy.convert` checks it), at
  most zoom 17 (16 for one point), not again within 2 s of a frame; never on a poll where everything is in view.
  The expanded sheet hides the map: it frames once the sheet comes down. Reduce Motion: no animation.
- **Trip alerts** (`Model/BusAlerts.swift`): before boarding "Red Line: Bus 101 is 2 stops away" / "... is
  approaching Ratner Center" (body "Board at X. Arrives in about 4 min (est.)." + "You may not make it on foot."),
  "arriving at X in about 7 min (est.)" with the minutes choice; on board "Get off in 2 stops: X" then "Get off at the
  next stop: X" (body "Red Line, Bus 101. Your stop in about 3 min (est.)."), once per ride. The 2 stops / 1 stop /
  minutes / in-app choices apply to station and trip alerts alike. Station alerts pause during a trip with trip alerts
  on ("Paused during your trip: alerts follow your trip's bus."). Live data down: ONE "Live data delayed" alert per
  outage (trip and station), only on the feed's own evidence (a failed poll, or a fresh poll of an old feed): never
  for data that only aged in the background. Notifications: thread "trip" / "bus-alerts", the body ends with
  " Unofficial.", the in-app banner when not allowed. Permission: asked at Start when trip alerts are on and it was
  never asked (or when a station is chosen); never at launch, never in `-demo`; alerts wait for the answer. Simulated
  buses never alert.

### Map labels: building and place names (owner request 2026-10-13)

"If possible, the buildings on the maps should also have their names like Google maps. Not every building, but highly
trafficked ones and promanent off campus locations relevant to the bus coverage should have names on the map
displayed by default", and "Other locations that need naming is UChicago dorm buildings". Same data and rules as the
web (web/js/map/landmarks.js, docs/ARCHITECTURE.md "Map labels"):
- **Data:** the bundled `web/data/landmarks.json` (87 names: tier 1 = the busiest hubs, every UChicago dorm, the stop
  namesakes, groceries, Metra / Green Line stations, MSI, the Obama Center, Gleacher Center; then 2 and 3), decoded by
  Kit `Landmarks.parse` (missing or bad file = no names, bad rows dropped, optional `until`). Bundled only: the names
  are curated, so they are not part of the daily schedule download (`ScheduleUpdater.files` is unchanged).
- **Which:** tier 1 from zoom 13.75, 2 from 16, 3 from 17 (2026-10-14, owner: the detailed names a little closer in),
  in the web's (Leaflet) zoom, measured from the ground
  scale at the center of the visible map (a rotated map keeps it). Deviation: the web starts tier 1 at 14.5 because it
  opens at 15; the iPhone opens wider (`MapCameraModel.campus`, zoom 14.1 to 14.4 by width), so tier 1 starts at 13.75
  to be on at the opening camera. `until` hides "Max Palevsky Commons" from 16, when Max Palevsky East / Central /
  West (tier 2) show.
- **Where** (Kit `Landmarks.place`, `MapScreen.layoutLabels`): priority order (tier, then the file's order); centered on
  the building, else one of 8 sides at 4 pt, else at 14 pt, never farther; the padded box (2 pt) must fit inside the
  visible map (below the floating chrome, above the sheet: the web uses its whole map) and cover no name already placed
  and no obstacle; no spot = left out until you zoom in. Obstacles: every stop (the web's 13 pt square; favorite stars
  and rings larger) and, on the iPhone only, the trip's stop labels, "You (est.)" at the boarding stop, the
  destination marker, your location and the locate button. Buses are not obstacles (they move every poll; names
  would blink, and the CI shots would depend on the simulated buses); they are drawn over the names. Skipped from the
  web: "avoid the basemap's street names" (`textAt`): MapKit does not tell where it draws its street names.
- **Text:** bold system font, tier 1 11.5 pt at zoom 14.5 to 14.5 pt at 18, tiers 2 and 3 11 to 14 pt (web
  labelSize); Dynamic Type up to 1.25x (from xxxLarge on, the accessibility sizes included), never smaller. Wrapped at
  8.5 em; line height 1.12 em. Widths are estimated, not measured (Helvetica Bold metrics x 1.12; a Kit test measures
  every name with CoreText in SF Pro and checks the estimate is never narrower). Colors `Palette.mapLabel` (#2C4A66 /
  #BCD0E2) with a halo and a faint plate (the halo color, white / #18181B, at 50%, corner radius 5).
- **Drawing** (`Views/MapScreen.swift` `LandmarkLabel`): text-only `Annotation`s declared first, so stops, buses, the
  trip and you are drawn over them; never take a tap (`allowsHitTesting(false)`), hidden from VoiceOver (stops and
  buses keep their labels); never animated. Laid out at camera END: every frame of a move only notes the time
  (`onMapCameraChange(frequency: .continuous)` -> `MapLabelModel.cameraMoved`) and the layout runs once the camera has
  been still for 0.3 s; also when the app moves the camera (fit, fly to, the follow frame), when the visible map
  changes size, when the stops / trip labels / destination change, when the landmarks load and on a text size change
  (`LabelWatcher`), each time again 0.5 s and 1.2 s later (`MapLabelModel.layoutSoon`). Why not `.onEnd` alone: with
  it, the first CI shots kept the names of an earlier camera after the app's 0.6 s camera glides (names cut at the
  screen edge, none on the Main Quad). Never a layout per frame or per bus move. The
  result lives in `AppModel.mapLabels` (`MapLabelModel`) and is assigned only when it changes; a name that changes side
  or size is a new annotation (`drawKey`). Apple's own points of interest stay off (`pointsOfInterest: .excludingAll`),
  so no place is named twice. CI shots: 36-map (opening camera), 37-map-near (`-screen near`), 38-trip-map, and the UI
  test's 39-map-zoomed / 40-map-panned.

### Live Activity times (owner decision 2026-10-11)

Never seconds for an estimated arrival (ship checklist item 2, no invented precision), and right while the app is not
running: there is no push server, the activity is updated locally (`pushType: nil`) while the app is open (on change,
at least every 60 s, when the arrival enters its last minute, once on the way to the background). Between updates
the system draws the activity only at its stale date, which is 120 s after the data, or the start of the last minute
when that comes first (Kit `LiveTripSnapshot.staleDate`). What the arrival shows (`Shared/LiveTripViews.swift`
`LiveETAMode`, decided when the system draws it):
- **iOS 18 and later:** "4 min" that the system counts down itself (`Text(TimeDataSource.dateRange(endingAt:),
  format: Date.ComponentsFormatStyle(style: .abbreviated, fields: [.minute]))`: whole minutes, floored like every
  ETA in the app, never below "0 min"), with the clock time "6:37 PM" (Chicago time, `TimeFmt.clock`) under it.
- **iOS 17** (no minute-precision self-updating text; the deployment target): the clock time "6:37 PM" is the main
  value, with "4 min as of 6:33 PM" under it, the minutes of the last update said as such. Never a frozen countdown.
- **Under a minute** (both): "Now", the app's ETA word, with the clock. The stale-date redraw at the start of the last
  minute is what says it while the app is closed ("~Now" with "Data delayed, times may be off").
- **Stale** (no update for 120 s, both): "~6:37 PM", no minutes, "Data delayed, times may be off", dimmed.
The headline drops its minutes ("Next 53RD at Reynolds Club"): the arrival sits next to it. `-screen livestates` / `livestatesend` (CI
gallery "28-livestates", "29-livestates-end") draws the card in all four states plus the minute format at 272 / 119 / 61 / 59 / 0 s.

## Build and run on a Mac

1. Xcode 26+ (iOS 26 SDK: App Store uploads need it since 2026-04-28; the deployment target stays iOS 17) and
   `brew install xcodegen`.
2. `ios/scripts/bootstrap.sh` (renders the icon, runs `xcodegen generate`), then `open ios/StraightBussing.xcodeproj`.
3. Pick an iPhone simulator, Run. For simulated buses add `-demo` under Product > Scheme > Edit Scheme > Arguments.
4. Kit tests: `cd ios/StraightBussingKit && swift test` (or the Test action in Xcode on the package).
5. On a real iPhone: set your Team (the bundle id is `SB_BUNDLE_ID` in `project.yml`), then Run. Live Activities need iOS 16.1+;
   the Dynamic Island needs an iPhone 14 Pro or later.

App launch in the CI simulator (iPhone 17 Pro, iOS 26.5, debug build, demo mode; seconds, average / best). These two
runs were on different runner machines, so read them as "no regression", not as a speed-up; the launch path itself
did not change (decode off the main thread before and after):

| UI timing | before (old app, run 38075346530) | after (main run 38094622240) |
|---|---:|---:|
| Launch to first frame (`XCTApplicationLaunchMetric`, 5 runs) | 4.58 / 3.26 | 4.09 / 2.40 |
| Launch to "next bus at the nearest stop" shown (3 runs, includes XCUITest's idle waits) | 8.36 / 7.25 | 6.59 / 5.92 |

On a real iPhone a release build is several times faster; the simulator numbers are for spotting regressions.

What changed:
- Place search (per keystroke, the worst path): normalized text is ASCII, so names, nicknames and categories keep
  their bytes from the index build and are compared as bytes (no String prefix / Foundation `contains`, no array
  per word, no array per place); `norm` has an ASCII fast path (no Unicode decomposition: also the index build at
  launch); the spelling distance uses a precomputed 128 x 128 substitution table and reused buffers instead of two
  dictionary lookups and three allocations per vocabulary word. Same results: the 94 UChicago queries and every
  spelling test pass unchanged.
- Planner: the ride cache is keyed by (route, first, last stop index) instead of a joined string of the whole path;
  the loop time per route is computed once per plan.
- Launch: the bundled (or downloaded) data is decoded off the main thread (as before) and the first paint never
  waits for it; the schedule check runs after boot, off the main thread.
- Per poll: only the observed slices that changed are written (as before); map stop markers are `Equatable` on what
  they show (`StopDot` + `.equatable()`; its tap closure is new on every map body), so SwiftUI skips all ~90
  unchanged stop views when the map body re-runs for moving buses; the plan and ring sets are computed once per map
  body instead of once per stop. Annotation content never reads the model from the environment (MapKit hosts it
  outside the normal view tree).
- Map counts: route lines and stops are cached per visibility change (as before); direction chevrons are capped at
  40 per shape line (the two longest routes, 33 km and 25 km, had 104 and 77 SwiftUI annotations each).
- Memory: every cache is bounded: sidewalk routes 256 entries, oldest dropped first (it grew for the whole session),
  bus-leg paths 64, Photon 30 queries, the clock formatter one per time zone and locale, fired bus alerts capped.
- Battery and network: the live feeds use one ephemeral `URLSession` without a URL cache (every poll has a new
  cache-busting URL, so the shared session wrote a new disk cache entry every 10 s), no cookies, 8 s request /
  15 s resource timeouts, no waiting for connectivity (offline fails at once and the pill says so), one warm
  HTTP/2 connection; 20 s polls in Low Power Mode; no polling and no clock tick in the background; a request
  cancelled by going to the background is not counted as a feed failure. Location: when-in-use, 10 m accuracy with
  a 30 m distance filter (15 m during a started trip), never in the background.
- Rider safety: back in the app after a break, `now` and the freshness flags are updated before the first new poll
  is sent, so data from before the break never looks fresh (it shows "Last known" / the pill until the poll lands).
- Main thread: JSON decode, planning, refining, search, the schedule download and validation all run off it; the
  main thread only assigns results.

## Schedule updates (fresh data without an app update)

The app bundles `web/data` at build time, but the web app's data refreshes daily (pages.yml runs
`tools/build_gtfs.py` on every deploy and at 09:17 UTC). Kit `ScheduleUpdate.swift` keeps the iPhone current:
- At launch (after the first paint, off the main thread) and on every return to the app, `ScheduleUpdater` checks
  if a check is due (at most once a day; one hour after a failure). It sends one conditional GET for
  `https://blobberus.github.io/straight-bussing/data/meta.json` (If-None-Match / If-Modified-Since). A 304, or a
  `generated_utc` that is not newer than the data in use, ends the check: about 120 bytes.
- Only when it is newer: the 7 schedule files (routes, stops, shapes, route_stops, stop_addresses, service,
  segments; about 20 KB compressed) in parallel. The set is used only if every file downloaded and
  `StaticValidator` passes: required files readable, routes / stops / route stops / shapes / service hours not empty,
  a readable schedule date newer than the one in use, every route_stops route and stop known, shapes and service
  only for known routes, every stop within 50 km of campus. Then it is written atomically to
  `Library/Caches/schedule/current/` (new folder first, then swapped in) with `state.json` (dates, validators).
- places.json (about 50 KB compressed) is checked at most weekly the same way (at least 100 places, all near campus,
  newer date).
- At launch `ScheduleStore.loadBest` uses the downloaded set only when it is newer than the bundled one and still
  valid; a damaged or outdated download (an app update bundled newer data) is deleted and the bundled copy is used.
  If iOS purges Caches, the bundled copy is used until the next check.
- A new schedule is swapped in right away unless a trip is started or Directions is open (then after the next poll
  that finds neither); prefs, map order and favorites stay. About shows the date of the data in use ("Schedule data
  from Oct 10, 2026", like the web).
- Privacy: plain GETs of public files with no query, no cookies, no location, search text or identifier; skipped in
  Low Data Mode (`allowsConstrainedNetworkAccess = false`: optional data); off in `-demo`. About's Privacy list says
  so. Tests: `ScheduleUpdateTests` (validation, fallback, once a day, 304, failed / invalid downloads, offline).
